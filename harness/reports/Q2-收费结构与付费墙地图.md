## 1. 摘要 TL;DR

1. 档位只有三档：**Developer（$0/seat）→ Plus（$39/seat/月）→ Enterprise（定制）**，外加面向 VC 的 Startup 计划（**两档：Build 席位折扣 / Scale $10,000 credits·1 年**）。
2. 计量有两套并行：**trace 数量**（Observability & Evaluation 主口径）+ **LSU（LangChain Standard Units，1 LSU = $1）**（Deployment / Engine / Fleet / Sandboxes / Gateway 的统一口径）。
3. **免费额度**：Developer 5,000 base traces/月、1 seat；Plus 10,000 base traces/月、无限 seat；Enterprise 定制。**Developer 档的每月唯一 trace 上限 5,000 仅适用于"无付款方式"的用户**。
4. **「账号 ≠ 付费」是本题最关键的一条**：Developer 档 $0 但**必须注册账号拿 API key**，且 Local Studio（连本地 `langgraph dev`）也强制要求账号。也就是说 LangSmith 的**观测层是「免费但需账号」**，这正是本项目要摆脱的那一层。
5. **付费墙精确形状（DOM 级解析 74 行勾选矩阵后确定）**：**Developer 档实际可用 31 个勾选项（29 个产品功能 + 2 个支持渠道）**（含 Tracing / Monitoring / Evals / Datasets / Annotation Queue / Prompt Hub / **Studio** / **Fleet 全套** / **Sandboxes 全套** / **LLM Gateway 全套**）。真正被锁住的是 **5 类**：**① Deployment 的托管与扩缩（整行 N/A）② Engine（整行 N/A）③ Tuned Evaluators（整行 N/A）④ Insights ⑤ Bulk data export（Plus 也锁，仅 Enterprise）+ Unlimited agents**。
6. 对 opengraph 的判断 ①：**付费墙精确落在"托管与自治"层，不在"图运行时 + 本地观测 + 本地调试 IDE"层**——opengraph 瞄准的正是后者，因此可以在完全不碰任何付费墙的前提下做出等价物。
7. 对 opengraph 的判断 ②：**"免费但需账号"必须被 opengraph 消灭**。opengraph 的零账号能力本身就是对 LangSmith 免费档的**直接替代**，这是比"功能更多"强得多的卖点。
8. 对 opengraph 的判断 ③：opengraph 不应引入任何配额/seat/LSU 概念；若未来要收费，只能对"托管的 opengraph Cloud"收费，**内核必须永远免费且离线**。

## 3. 正文

### 3.1 三档套餐（官方原文关键字段）

[来源: P1，as-of 2026-11-01]

| 档位 | 席位价格 | 目标用户 | 官方描述 |
|---|---|---|---|
| **Developer** | **$0 / seat per month**，then pay as you go | "For solo users getting started." | 1 seat；5k base traces/月；Community support |
| **Plus** | **$39 / seat per month**，then pay as you go | "For teams building and deploying agents." | 无限 seat；10k base traces/月；Access to Deployment, Engine, and more |
| **Enterprise** | **Custom pricing** | "For teams with advanced hosting, security, and support needs." | 自托管/混合部署、SSO/ABAC/RBAC、SLA、自定义 seat 与 workspace |

计费周期：Developer / Plus 按月 self-serve（每月 1 号或按比例）；traces 按月后付；**Enterprise 按年预付** [来源: P1 FAQ "When will I be billed?"]。

### 3.2 三种计量单位并存（这是 2026 年的关键变化）

| 计量单位 | 定义 | 适用功能块 | 免费额度 |
|---|---|---|---|
| **base trace** | 一次操作（一个 agent / evaluator / playground session）的全部 run 集合 | Observability & Evaluation（tracing、evals、monitoring、datasets） | Dev 5k/mo、Plus 10k/mo、Enterprise 定制 |
| **extended trace** | retention 从 14 天升级到 180 天的 trace，**单独计费** | 同上 | 无（按量） |
| **LSU**（LangChain Standard Units） | **1 LSU = $1**，"a unit of work"，跨产品统一 | Deployment / Engine / Fleet / Sandboxes / LLM Gateway / Tuned Evaluators | 见下表 |

**保留期分档**（P2）：Base = 14 天；Extended = 180 天。2026-09-14 起 SaaS 客户 extended 上限调整为 180 天 [来源: P2 "Data retention auto-upgrades" 提示框]。

**LSU 免费额度**（P1）：

| 功能 | Developer | Plus | Enterprise |
|---|---|---|---|
| Fleet | 含 **7 LSU**/月（用尽则暂停新 run） | 含 **37 LSU**/月 | 定制 |
| Sandboxes | 含 8 LSU + 限 10 个沙箱 | 按量（含 8 LSU 免费） | 定制 |
| Engine | **N/A** | 按量（每次 run ≈ 7–45 LSU，每 6 小时调度一次） | 定制（记入承诺 credits） |
| Deployment | **N/A** | 含 1 个免费 Serverless(Small) | 定制 |
| LLM Gateway | 按量（Gateway Credits） | 含一定量 Gateway controls + 按量 | 定制 |
| Tuned Evaluators | **N/A** | 按量（Perceived Error 0.015 LSU / Evaluation Run） | 定制 |

**Deployment 资源费率**（P1，Plus 档）：Runtime Compute 0.0675 LSU/vCPU-hr、Runtime Memory 0.0090 LSU/GiB-hr、Database Compute 0.177 LSU/vCPU-hr、Database Memory 0.025 LSU/GiB-hr。

**Deployment 规格**（P10 `cloud-platform-features#sizes`，GCP 计价口径；Redis 不计费）：

| 容器 | Serverless S | Serverless M | Serverless L |
|---|---|---|---|
| API server | 0.4 vCPU / 1 GiB | 2 vCPU / 2 GiB | 4 vCPU / 4 GiB |
| Queue worker | 0.4 vCPU / 1 GiB | 2 vCPU / 2 GiB | 4 vCPU / 4 GiB |
| **可计费运行时合计** | **0.8 vCPU / 2 GiB** | **4 vCPU / 4 GiB** | **8 vCPU / 8 GiB** |
| Database | 共享多租户 | 共享多租户 | 共享多租户 |

| 容器 | Dedicated S | Dedicated M | Dedicated L |
|---|---|---|---|
| API server（每副本） | 1 vCPU / 2 GiB | 2 vCPU / 4 GiB | 4 vCPU / 8 GiB |
| API server 副本数 | 2–10 | 2–20 | 2–40 |
| Queue worker（每副本） | 1 vCPU / 2 GiB | 2 vCPU / 4 GiB | 4 vCPU / 8 GiB |

> Serverless 单副本不横向扩出，队列 worker 默认最多 10 个并发 run（`N_JOBS_PER_WORKER` 可调），其余排队 [来源: P10 "Serverless"]。**Deployment 类型创建后不可变更**（规模可改）[来源: P10 "Immutable deployment type"]。

### 3.3 限流（也是"免费"的一部分）

[来源: P2 "Rate limits"；P9 `administration-overview` 同节复核]

| 限制 | Developer（无付款方式） | Developer（有付款方式） | Startup/Plus | Enterprise |
|---|---|---|---|---|
| 每小时 trace event | 50,000 | 250,000 | 500,000 | 定制 |
| 每小时 trace 数据摄取 | 500MB | 2.5GB | 5.0GB | 定制 |
| 每月唯一 trace 数 | **5,000**（仅无付款方式时） | — | — | — |

通用限流：`POST/PATCH /runs*` 5000/min、`*/feedbacks*` 5000/min、`*` 2000/min、`GET /runs/:id` 30/min、`DELETE /sessions*` 30/min；单条 trace 最多 25,000 runs。

**新增：per-project / per-user 限额**（P9）：除 workspace 级与套餐级限额外，组织管理员还可为**单个 tracing project 或单个 workspace 成员**设置每月 trace 上限；触限后新 trace **被丢弃**且不会重新摄取，直至限额重置（按 UTC 自然月）。限额为**近似执行**，可能略超。对 Cloud 与 Self-hosted 均适用。

### 3.6 「免费但需账号」的具体表现（必须写进 opengraph 的替代方案）

1. **Studio 强制账号**：官方文档写明前置条件是 "A LangSmith account" + "A LangSmith API key" [来源: harness/docs/oss/python/langgraph/studio.md:13-16]。而 `langgraph dev` 的 banner 会打印 `🎨 Studio UI: https://smith.langchain.com/studio/?baseUrl=http://127.0.0.1:2024` [来源: P5:88；源码 `langgraph_api/cli.py:306-307`]——**本地开发的调试 UI 也要过云**。**且 Studio 本身在 Developer 档免费** → 这不是"付费才能用"，而是"免费但强制过云"。
2. **Tracing 默认需要 key**：`langgraph_api/config/__init__.py:675-677` 明确写着"if langsmith api key is set, enable tracing unless explicitly disabled"——即 **API key 会自动打开 tracing**（这正是 opengraph 要彻底避免的反面教材）。
3. **自托管 Standalone server 仍需 license key + 出网**：P4 前置明确要求 `LANGSMITH_API_KEY`、`LANGGRAPH_CLOUD_LICENSE_KEY`，并且 "Egress to `https://beacon.langchain.com` ... required for license verification and usage reporting"。源码 `langgraph_api/metadata.py:75` 定义 `BEACON_ENDPOINT = "https://beacon.langchain.com/v1/beacon/metadata/submit"`，`metadata.py:173-176` 表明无 license key 时跳过上报。
4. **Sandboxes 默认 restricted egress**：非 Enterprise 组织默认受管控出网限制，"LangSmith blocks destinations outside the allowlist, even if you add them to a sandbox's proxy configuration"；需 unrestricted egress 须提交 support ticket [来源: P13 `sandboxes`]。
5. **Agent Registry 自托管不可用**：想在自托管环境做 agent 目录 / environment 分级，官方没有替代方案 [来源: P13 `agent-registry`]。

> 结论：**"自托管"并不等于"零账号"**——即便 standalone 部署，也要 license key（付钱买）+ beacon 出网。这是一个常被忽略的付费墙，opengraph 的"完全离线"定位正好跨过它。

## 5. 对 opengraph 的直接启示（可执行）

1. **把「免费但需账号」当作 opengraph 的核心替代目标写进 README**，具体到四个动作可替代：① tracing 数据落本地文件而非 `smith.langchain.com`；② Studio UI 改为 `opengraph studio` 打开 `127.0.0.1`；③ Prompt Hub / Annotation Queue 改为本地文件 / SQLite；④ 不需要任何 API key。
2. **opengraph 必须在内核层做"环境变量免疫"**：不读 `LANGSMITH_*`、不读 `LANGCHAIN_*`、不读 `ANTHROPIC_API_KEY` 之类。LangChain 的反面教材是 `langgraph_api/config/__init__.py:675-677`——**API key 存在即自动开 tracing**。opengraph 应反过来：**环境变量存在也不改变任何行为**（除非用户显式传入 tracer 对象）。
3. **不要在 opengraph 引入 trace 数量配额**。LangSmith 的"5000 traces/月"限流 + per-project/per-user 限额是 SaaS 稀缺性设计；opengraph 本地存储无此约束，这是可以主动宣传的差异点。
4. **若 opengraph 未来做 SaaS 托管版**，可复刻 LSU 计量思路（1 LSU = $1 的抽象单位最省沟通成本），但**内核必须永远 MIT + 离线**。
5. **"自托管≠零账号"** 这个事实应写进 opengraph 的对比文档：LangGraph 的 standalone server 仍需 `LANGGRAPH_CLOUD_LICENSE_KEY` 且要向 `beacon.langchain.com` 出网（P4 + `metadata.py:75`），opengraph 的 standalone 是零 license、零出网。
6. **opengraph 可以合法地覆盖 LangSmith 免费档 29 个产品功能中的绝大多数**（Tracing / Monitoring / Evals / Datasets / Annotation Queue / Prompt Hub / Studio / MCP / 实时流式）——**这不是"挑战"，而是"等价替代"**。建议 README 用一张"LangSmith Developer 档功能 → opengraph 替代方案"对照表，把定位讲清楚。
7. **Fleet / Sandboxes / LLM Gateway 即使在 Developer 档开放，也不进 opengraph 范围**：三者都会引入真实出站（模板拉取、沙箱执行代码、模型调用代理），与"零出站"承诺冲突。
