## 1. 摘要 TL;DR

1. **好消息：整个 LangChain 家族的 OSS 部分全部是 MIT**（`langgraph`、`langchain`、`langchain-core`、`langsmith` SDK、`langchain-classic`、所有 provider 包）——**无 AGPL / SSPL 类传染性条款**。商用友好度：**高**。
2. **唯一的非 MIT 陷阱是 `langgraph-api` 与 `langgraph-runtime-inmem`**（**Elastic License 2.0**）。ELv2 明确禁止 "provide the software to third parties as a hosted or managed service"。**这两个包不能进 opengraph 的依赖树，也不能被 opengraph 的托管版内嵌。**
3. **LangSmith SaaS 平台本身不是开源软件**，受 LangSmith Platform License 约束（付费订阅）。但 **LangSmith 的 SDK（`langsmith` 包）是 MIT**——**"开源 SDK + 付费平台"是 LangChain 的商业模式核心，也是 opengraph 存在空间的来源**。
4. **版权与 API 名称**：MIT 允许复制/修改/分发（含闭源商用），**唯一要求是保留版权声明与许可声明**。因此 opengraph 可以自由实现 `StateGraph` / `add_node` / `add_edge` / `START` / `END` 等 API 名称——**API 名称本身不受版权保护**（版权保护表达，不保护思想/接口/方法论）。
5. **商标是真正的风险点**：不能使用 "LangGraph" / "LangChain" / "LangSmith" 作为 opengraph 的产品名或暗示官方关联；文档中提及需用"兼容 / 类似 / 受启发于"这类表述并加免责声明。
6. 对 opengraph 的判断 ①：**opengraph 应选 MIT 或 Apache-2.0**（推荐 Apache-2.0——含**专利授权**与**明确的双许可条款**，对"复刻他人 API"的场景更稳）。当前仓库 `LICENSE` 已是 MIT（Copyright (c) 2026 杨家成），可保持。
7. 对 opengraph 的判断 ②：**必须在 README 与文档中加一节"与 LangChain 生态的关系"**，明确：① 非官方 ② MIT 许可的独立实现 ③ 不使用 LangChain 商标 ④ 不含任何 LangSmith 代码或运行时依赖。
8. 对 opengraph 的判断 ③：**代码层面必须避免任何来自 `langgraph-api` / `langgraph-runtime-inmem` 的复制**（ELv2），包括其 API 协议实现细节；如需实现"Agent Server 协议"，应依据**公开文档/公开 OpenAPI 规范**独立实现。

### 3.2 「付费墙」在许可证层面的真实形状

**这是本题最有价值的发现**：LangSmith 的付费墙**不是靠许可证锁住的，而是靠"服务端是专有的"锁住的**。

| 层次 | 是什么 | 许可证 | 付费性质 |
|---|---|---|---|
| 客户端 SDK | `langsmith` PyPI 包 | **MIT** | 🟢 **完全免费** |
| LangGraph 运行时 | `langgraph` + `langgraph-prebuilt` + `langgraph-checkpoint*` | **MIT** | 🟢 **完全免费** |
| Agent Server 运行时 | `langgraph-api` + `langgraph-runtime-inmem` | **Elastic-2.0** | 🟡 可免费自用，**不可转售托管** |
| 控制面 / 数据面 / Studio UI / 评测平台 | LangSmith SaaS | **专有** | 🔴 **付费** |

**含义**：

1. **如果 opengraph 只想做"本地图运行时"，它甚至不需要碰任何许可证问题**——MIT 允许完全自由地参考与重写。
2. **如果 opengraph 想提供"托管的 Agent Server"（对标 LangSmith Deployment / 自托管控制面），就会直接撞上 ELv2**：不能把 `langgraph-api` 原样打包成托管服务。**opengraph 必须自己写一份 Agent Server**（这也是 Q3 §3.5、Q6 路线 B 强调"自己做本地 server"的原因之一）。
3. **LangSmith Platform License 的 2.4 条**（D7）明确禁止对 LangSmith Platform 本身做 "decompile, disassemble, reverse engineer, translate, adapt, modify, or create derivative works" 及 "sell, resell, license, sublicense, distribute, rent, or lease"——**这只约束 LangSmith 平台（服务端），不约束 MIT 的 `langsmith` SDK 与 `langgraph` 包**。

### 3.3 版权：复刻 API 名称与接口的注意事项

#### 3.3.1 可以做什么（MIT 授权范围）

MIT 许可条款允许：使用、复制、修改、合并、发布、分发、再许可、**销售**。唯一条件：**在所有副本或实质性部分中保留版权声明与许可声明**。

因此 opengraph 可以合法地：

| 行为 | 合法性 | 说明 |
|---|---|---|
| 实现同名 API（`StateGraph` / `add_node` / `add_edge` / `add_conditional_edges` / `compile` / `invoke` / `START` / `END`） | ✅ | **API 名称与签名不受版权保护**（版权保护的是具体表达：源代码文本、文档措辞、图形设计） |
| 复制 LangGraph 的源码片段 | ✅ | 必须在文件头保留 `Copyright (c) 2024 LangChain, Inc.` + MIT 全文 |
| 复制 `draw_mermaid` 的输出格式（Mermaid 语法） | ✅ | 语法是"事实/方法"，非表达 |
| 参考 Pregel 算法实现自己的运行时 | ✅ | 算法不受版权保护 |
| 参考 LangSmith 的数据模型（run/trace/thread） | ✅ | 概念不受版权保护；**但不要复制其 UI 视觉资产** |
| 把 MIT 源码集成进闭源商业产品 | ✅ | 保留声明即可 |

#### 3.3.2 不该做什么（风险项）

| 行为 | 风险 | 建议 |
|---|---|---|
| 直接复制 `langchain_core/runnables/graph_mermaid.py` 的 mermaid 渲染代码 | 🟡 低（MIT 允许，但会带入 300+ 行第三方代码与风格包袱，且未来 `langchain-core` 升级会产生同步义务——虽然 MIT 无同步义务，但维护成本上升） | **独立重写**（Q3 §5 建议 2） |
| 复制 `langgraph-api` 的任何代码 | 🔴 **高**（ELv2，非 MIT；且 ELv2 禁止托管） | ❌ 一律不碰；仅依据公开 OpenAPI 规范独立实现 |
| 复制 LangSmith Studio 的前端代码 / 视觉设计 | 🔴 高（专有；且商标） | ❌ 只参考功能，不复制表达 |
| 复制 LangSmith 品牌素材（logo、配色、图标） | 🔴 高（商标） | ❌ |
| 在产品名中使用 "Lang"/"LangChain"/"LangSmith"/"LangGraph" | 🔴 **高**（商标 + 混淆风险） | ❌ 用 "opengraph"；文档提及时用"LangGraph-compatible / inspired by" |

#### 3.3.3 商标注意事项

**（a）官方已公开发布品牌资产与使用指南（D10，`https://www.langchain.com/brand-assets`，2026-11-01 抓取）**

该页标题为 "Brand Assets - LangChain Logos & Usage Guidelines"，其 JSON-LD 描述为："Official brand assets for LangChain and its products. All logos are approved for use in documentation, presentations, press coverage, and community content, **subject to the usage guidelines**."

页面明确将 logo 分为四类，且把 **langgraph / deepagents 与 langchain 并列为"Open Source Framework Logos"**：

| Logo 分类 | 包含 | 官方说明 |

| **Core Logos** | LangChain、LangSmith（各含 light / dark 变体） | "Our core logos: LangChain and LangSmith, in light and dark variants for any background." |
| **Open Source Framework Logos** | langchain、**langgraph**、**deepagents** | "Logos for our open source frameworks: langchain, langgraph, and deepagents" |
| **Community Logo** | 社区活动用 | "Please do not use as a substitute for the official LangChain logo." / "Don't use the Community logo in place of the official LangChain logo, or in a way that implies LangChain runs a community-organized event or piece of content." |

**官方 Do's（可做）** [来源: D10]：
- 把 logo lockup 锚定在页面/框架边缘，留出约等于标志本身高度的净空；
- 保持 lockup 的锁定比例、尺寸与间距；
- 每个标志配各自的 wordmark（LangChain 配 LangChain，LangSmith 配 LangSmith）；

**官方 Don'ts（不可做）** [来源: D10]：
- 不要拉伸或包裹 logo；
- 不要使用 off-brand 配色；
- 不要施加效果（含描边、缩放或重排元素）；
- 不要放在对比度或净空不足的背景上；
- 不要用 Community logo 代替官方 LangChain logo，或暗示 LangChain 主办。

**官方描述文案（"Approved copy"，指定用途需按原文使用）** [来源: D10]：
> "LangChain enables every company to own their intelligence. LangChain's open, model-agnostic harnesses give teams choice and control over how they build their agent architecture. LangSmith brings testing, deployment, and monitoring together so teams can continuously improve their agents, compound intelligence, and govern them at scale."

页面还给出官方联系渠道 `press@langchain.dev`（"Need something that isn't here? Email us and we'll sort it out."）。

**（b）D12/D7 的 ToS 明确保留商标权**："alter or remove any trademarks or proprietary notices contained in or on the LangSmith Platform or Documentation" 属禁止行为。这说明 LangChain 积极主张商标。

**（c）通用法律原则（需律师审阅，非抓取可解决）**：
- **API 名称**（`StateGraph`、`add_node`）通常**不构成商标侵权**——它们是功能性标识，用于指代同类接口（"nominative fair use"），这是开源生态互操作的通行做法。
- **产品名/品牌名**（"LangGraph" 作为 opengraph 的产品名，或宣传语中暗示官方关联）**风险高**。
- **Logo、图标、配色、界面视觉**受商标/外观设计保护，**不可复制**。→ 由 (a) 的官方指南直接证实。

**（d）必须做的四件事**：
1. README 顶部加明确的"非官方 / independent implementation"声明。
2. 不在任何地方使用 LangChain / LangGraph / LangSmith / deepagents 的 logo 或品牌色（含不以"未变形"方式使用）。
3. 文档中提及第三方时用"兼容（compatible with）""受启发于（inspired by）""类似（similar to）"的表述，并附一条免责条款。
4. **不要复制官方"Approved copy"文案**——那是官方指定用于 press/deck/事件/文档的**approved copy**，照抄会让读者误以为 opengraph 是官方出品。

#### 3.3.4 商标与许可的结论

> **可以复刻 API，但不能复刻品牌。**
> 许可证（MIT）解决"能不能抄代码"；商标解决"能不能叫这个名字"。**两者独立**。
> opengraph 的具体做法：**API 层全面兼容（同名同签名）+ 品牌层完全独立 + 许可证层选 MIT/Apache-2.0 + 零 `langchain*` 依赖（这同时规避了 §2.6 的剥离要求）**。

### 3.4 opengraph 自身的许可证选择建议

| 选项 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **MIT**（当前） | 最宽松、最广兼容、Python 生态惯例 | **无显式专利授权** | 🟡 可用 |
| **Apache-2.0** | 含**专利授权**（对"复刻他人 API"的场景更重要）、含"专利报复"条款、明确商标不授权 | 略啰嗦 | 🟢 **推荐** |
| BSD-3 | 宽松 | 无专利条款 | 🟡 |
| AGPL-3.0 | 强制开源 | **传染性**，会吓退企业用户 | ❌ 违背"商用友好"目标 |
| SSPL | — | **不是 OSI 认可**，且传染 | ❌ |

**建议**：从 MIT 改为 **Apache-2.0**，理由：
1. **显式专利授权**——opengraph 的核心价值主张是"复刻一套广为人知的接口"，专利风险虽低但非零，Apache-2.0 §3 给 contributors 提供专利授权。
2. **§6 明确写明商标不授权**——与 §3.3.3 的品牌策略呼应，把"商标不随许可转移"这件事写进法律文本。
3. Apache-2.0 附带 NOTICE 机制，便于在兼容实现中保留第三方归属声明。

> 若维持 MIT，也应在 README 单独写明"本项目不使用任何 LangChain 商标"。
