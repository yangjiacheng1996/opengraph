## 1. 摘要 TL;DR

1. **一个图运行时从外界真正需要的，只有 6 类东西**：① 状态 schema（含归约器）② 节点函数 ③ 边/路由函数 ④ 图结构描述 ⑤ 外部能力注入点（context / checkpointer / store / tracer）⑥ 可选的执行控制（interrupt / Command）。**没有模型抽象、没有消息类型、没有工具装饰器。**
2. **LangChain 特有 vs 通用协议的判别结果**：
   - **LangChain 特有（openchain 需适配）**：`AnyMessage` / `BaseMessage` / `add_messages` 归约器、`BaseTool` / `@tool`、`RunnableConfig` 的 `configurable` 约定、`langgraph_sdk` 的 `BaseUser`、`DeltaChannel`。
   - **通用协议（openchain 可直接采用）**：`Annotated[T, reducer]` 的二元归约器机制、`Annotated[list, operator.add]`、OpenAI 风格的 `tool_calls` 结构 `{"name","args","id","type"}`、`invoke(input) -> message` 的模型调用契约、`tool.invoke(args)` 的工具调用契约、路由函数返回节点名或结束标记、`Command(goto=..., update=...)`。
3. **图层不需要 LangChain**：实测 `langgraph` 的 `graph` / `pregel` / `channels` 模块对 `langchain_core` 的引用**全部集中在 4 类**：① `RunnableConfig`（26 处，配置传递）② `Runnable` 协议（`PregelNode` 实现它）③ `langchain_core.runnables.graph.Graph`（**唯一的图结构类型**）④ `callbacks` / `tracers`（可观测挂钩）。**没有一处依赖消息类型或工具类型。**
4. **因此 LangGraph 的图执行层是可以脱离 LangChain 的**——只需替换 `RunnableConfig` 与 `Graph` 两个类型。opengraph 要做的是**重新定义这两个类型**，而不是复刻 LangChain。
5. **最关键的实测发现（决定了契约设计）**：**节点收到的是普通 `dict`，且只包含"当前有值的 channel"**。实测 `NODE_INPUT_TYPE: dict`、`NODE_INPUT_KEYS: ['messages']`、`HAS_llm_calls: False`——这正是 `target.py:81` 里 `state.get('llm_calls', 0)` 能工作的原因。**opengraph 必须精确复制这个"稀疏 dict"语义**，否则 `state.get(key, default)` 会返回 `None` 而非 `default`。
6. 对 opengraph 的判断 ①：**opengraph 的内核契约应是「dict in / dict out + 稀疏状态 + 二元归约器」**，而不是"消息对象流"。所有消息/工具/模型概念全部外移到 openchain。
7. 对 opengraph 的判断 ②：**opengraph 应定义自己的 `RunConfig`（含 `thread_id` / `context` / `checkpoint_ns`）**，而不是复用 `RunnableConfig`——后者是 `langchain-core` 类型，一旦复用就把 `langsmith` 拖回来（Q3 核心结论）。
8. 对 opengraph 的判断 ③：**opengraph 应提供自己的 `Graph` 结构类型**（`get_graph()` 的返回类型），并提供 `draw_mermaid()`；这是 opengraph 唯一必须"重写而非复用"的 LangChain 特有件（Q3 §5 建议 2、Q7 §3.3.2）。

## 3. 正文

### 3.1 图运行时真正需要从外界拿什么（以 LangGraph 实现为参照）

按 LangGraph 的真实实现拆解，一个图运行时的输入面只有 **6 类**：

| # | 外部输入 | LangGraph 的具体形态 | 运行时用它做什么 |
|---|---|---|---|
| 1 | **状态 schema** | `TypedDict` / Pydantic model，含 `Annotated[T, reducer]` | 为每个 key 建立一个 **channel**（`LastValue` 或 `BinaryOperatorAggregate`）[来源: E1 `state.py:1820-1935`] |
| 2 | **节点函数** | `Callable[[StateDict], StateDict | Command]` | 每个节点订阅若干 channel，被触发时读到这些 channel 的当前值 |
| 3 | **边与路由函数** | `add_edge(src, dst)` / `add_conditional_edges(src, path_fn, path_map)` | `path_fn` 返回目标节点名（或 `END`） |
| 4 | **执行配置** | `RunnableConfig`（含 `configurable.thread_id` 等） | 定位 thread、传递 metadata/tags、注入 checkpointer |
| 5 | **外部能力注入点** | `checkpointer` / `store` / `cache` / `context_schema` | 持久化、长期记忆、缓存、运行时上下文 |
| 6 | **可观测挂钩** | callbacks / tracers | 记录 span |

**运行时内部的 4 个概念**（这些是 LangGraph 自己的，**不是外部契约**）：

- **channel**（`LastValue` / `BinaryOperatorAggregate` / `Topic` / `EphemeralValue`）[来源: E5]
- **Pregel actor**（`PregelNode`：订阅 channel → 读 → 写）[来源: E4]
- **super-step 循环**（Plan → Execution → Update）[来源: E12]
- **checkpoint 版本**（`checkpoint_id` / `checkpoint_ns`）

> **结论 1**：**模型抽象、消息类型、工具装饰器、provider 抽象、agent 装配——全部不在图运行时的契约面内。** 这印证了 §2.2 的两项目分工，也证明 opengraph 不需要 `langchain`。

### 3.2 逐项契约的技术细节（决定 opengraph 的实现）

#### 3.2.1 状态契约：稀疏 dict + 二元归约器

**归约器提取机制**（E1 `state.py:1905-1922`）：

```python
def _is_field_binop(typ):
    if hasattr(typ, "__metadata__"):
        meta = typ.__metadata__
        if len(meta) >= 1 and callable(meta[-1]):
            sig = signature(meta[-1])
            # 必须恰好 2 个位置参数
            if count(positional params) == 2:
                return BinaryOperatorAggregate(typ, meta[-1])
            else:
                raise ValueError("Invalid reducer signature. Expected (a, b) -> c. ...")
```

**默认归约器**（无 `Annotated` 时）：`LastValue`——**覆盖**（丢弃左值，保留右值）[来源: E5 `last_value.py:20-52`]。

**归约器调用语义**（E5 `binop.py:123-153`）：

```python
def update(self, values):
    if self.value is MISSING:
        self.value = values[0]; values = values[1:]
    for value in values:
        if overwrite: self.value = overwrite_value; continue
        self.value = self.operator(self.value, value)   # 二元调用
```

即 **`operator(current, new)`**，且支持 `Overwrite` 旁路（一个 super-step 内只允许一个 Overwrite）。

**稀疏状态语义**（E2 `read_channels`，`skip_empty=True`）：**channel 无值时该 key 根本不出现在节点入参 dict 里**。实测（E10）：

```
NODE_INPUT_TYPE: dict
NODE_INPUT_KEYS: ['messages']
HAS_llm_calls: False
state.get('llm_calls', 0) = 0
```

**这是 `target.py:81` 能工作的根本原因**，也是 opengraph 必须精确复制的语义。

**条件边读到的是"含本节点写入"的副本**（E3 `_algo.py:190-226`）：`fresh=True` 时，条件边函数看到的是"当前 channel 值 + 该节点本次写入"。**这意味着条件边可以在同一 super-step 内看到刚写的状态**——opengraph 若不实现这一点，`add_conditional_edges` 的语义会退化。

#### 3.2.2 节点契约

| 属性 | 契约 | 证据 |
|---|---|---|
| 入参形态 | **普通 `dict`**（不是对象、不是 Pydantic 实例，除非 schema 是 Pydantic） | E10 实测 `NODE_INPUT_TYPE: dict` |
| 入参内容 | **只含当前有值的 channel**（稀疏） | E10 + E2 |
| 返回形态 | **部分状态 `dict`**（只含要更新的 key）或 `Command` | E1 / E6 |
| 返回语义 | 逐 key 应用归约器：无归约器 → 覆盖；有归约器 → `operator(current, new)` | E1 + E5 |
| 返回中的未知 key | 触发 `InvalidUpdateError`（LangGraph 行为） | E1 `_get_channel` 校验 |

#### 3.2.3 路由契约

| 形态 | 契约 | 实测 |
|---|---|---|
| `add_edge(src, dst)` | 静态边；`src` 可为 `str \| list[str]`（多源 fan-out） | E1 |
| `add_conditional_edges(src, path_fn, path_map)` | `path_fn(state) -> str \| Hashable \| Sequence[Hashable]`；`path_map` 为 `dict \| list[str] \| None` | E1 签名 |
| `path_map` list 形式 | 返回值直接是目标节点名 | `target.py:131-135` |
| `path_map` dict 形式 | 返回值是 **key**，实际目标是 **value** | 实测 `PATHMAP_OUT: {'messages': ['C'], 'n': 3}`（route 返回 `"c"`，映射 `{"c":"c","d":"d"}` → 走 C） |
| 结束标记 | `END`（值 `'__end__'`）[E7] | 实测 |

#### 3.2.4 消息 / 工具 / 模型契约（**openchain 的适配面，不是 opengraph 的**）

| 契约 | 最小要求 | 通用 or LangChain 特有 | 证据 |
|---|---|---|---|
| **消息对象** | 节点只需读到 `.tool_calls` 属性；`tool_calls` 是 list，元素是 dict | `tool_calls` 结构 = **OpenAI 风格，通用**；消息基类 = LangChain 特有 | 实测 `AIMessage.tool_calls == [{'name','args','id','type'}]` |

| **模型调用** | `model.invoke(messages) -> AIMessageLike`；`model.bind_tools(tools) -> model` | **通用**（任何 chat model 协议） | `target.py:50,72` |
| **工具对象** | `tool.name`（str）、`tool.invoke(args) -> Any`、`tool.description` | **通用**（函数 + name 即可） | `target.py:49,96` |
| **tool_call 结构** | `{"name": str, "args": dict, "id": str, "type": "tool_call"}` | **通用**（OpenAI 规范） | 实测 |
| `AnyMessage` / `BaseMessage` 基类 | — | 🔴 **LangChain 特有** | `langchain_core.messages` |
| `add_messages` 归约器（按 id 去重/覆盖） | — | 🔴 **LangChain 特有** | `langgraph/graph/message.py:372-373` |
| `BaseTool` / `@tool` | — | 🔴 **LangChain 特有** | `langchain_core.tools` |
| `RunnableConfig` | — | 🔴 **LangChain 特有**（在 `langchain-core`） | `langchain_core.runnables.config` |
| `BaseUser` | — | 🔴 **LangGraph SDK 特有** | `langgraph/runtime.py:8` |
| `DeltaChannel` | — | 🔴 **LangGraph 内部特有** | `langgraph/channels/delta.py` |

#### 3.2.5 执行控制契约（`Command` / `interrupt`）

实测（E10 `test_contract2.py`）：

```
COMMAND_OUT: {'messages': ['B'], 'n': 5}
    → Command(goto="b", update={"n": 5})：既跳转又更新状态
INTERRUPT_OUT: {'messages': [], '__interrupt__': [Interrupt(value='need input', id='...')]}
    → interrupt(value) 抛出，run 返回 __interrupt__ 键
RESUME_OUT: {'messages': ['got:yes'], 'n': 1}
    → 用 Command(resume="yes") 恢复，从节点起点重跑
```

**契约要点**：

| 契约 | 最小要求 | 证据 |
|---|---|---|
| `interrupt(value)` | 抛出一个可识别的异常；run 结果含 `__interrupt__` 列表，元素含 `.value` 与 `.id` | E10 |
| 恢复 | 用 `Command(resume=...)` 从**节点起点**重跑（不是从 interrupt 点继续） | E10 + `langgraph/types.py:851+` 文档字符串 |
| `Command(goto=..., update=...)` | `goto` 目标节点名（或 `Command.PARENT`）；`update` 是状态更新 dict | E10 + `types.py:799` |
| `Send(node, arg)` | 条件边返回 `Send` → 以自定义 arg 调用目标节点（map-reduce 模式） | `types.py:704-720` |

### 3.3 图层是否真的需要 LangChain（依赖强度证据）

**Q8 必答点 3 的正面回答：不需要。**

#### 3.3.1 `langgraph` 对 `langchain_core` 的依赖面测绘（E9）

`langgraph/` 全目录共 **135 处** `langchain_core` 引用。按子目录与符号统计：

| `langchain_core` 符号 | 出现次数 | 性质 | opengraph 是否需要 |
|---|---|---|---|
| `runnables.RunnableConfig` | 26 | **配置传递**（`RunnableConfig` 只是 `dict` 的 TypedDict） | 🔴 **需替换**（定义自有 `RunConfig`） |
| `runnables.Runnable` / `RunnableBindingBase` | 8 | **协议**（`PregelNode` 实现它） | 🔴 **需替换**（opengraph 自有 `Node` 协议） |
| `runnables.graph.Graph` / `Node` / `Edge` | 5 | **图结构类型**（`get_graph()` 的返回类型） | 🔴 **需替换**（唯一必须重写的类型） |
| `runnables.config.*`（`var_child_runnable_config`、`run_in_executor`、`get_executor_for_config`） | 5 | 并发/配置工具 | 🟡 部分需要（并发执行器） |
| `tracers.*`（`LangChainTracer`、`_StreamingCallbackHandler`、`_V2StreamingCallbackHandler`） | 6 | **可观测挂钩** | 🟢 **用 OTel 替代** |
| `callbacks.*`（`BaseCallbackHandler`、`CallbackManager`、`ParentRunManager`） | 6 | **可观测挂钩** | 🟢 **用 OTel 替代** |
| `messages.*`（`AnyMessage`、`BaseMessage`、`ToolMessage`、`convert_to_messages`、`convert_to_openai_messages`） | 6 | **消息类型** | 🟢 **不需要**（鸭子类型） |
| `outputs.*`（`ChatGeneration`、`LLMResult`） | 2 | 模型输出类型 | 🟢 不需要 |
| `tools.*`（`BaseTool`、`@tool`） | 5 | 工具类型 | 🟢 不需要 |
| `language_models.*` / `embeddings.*` | 4 | 模型/嵌入类型 | 🟢 不需要 |
| `utils.pydantic.is_basemodel_subclass` | 1 | pydantic 辅助 | 🟡 可选 |
| `_api.beta` | 1 | 装饰器 | 🟢 不需要 |

**关键判定**：

1. **图执行语义（channels / Pregel 调度 / 归约器 / checkpoint）完全不依赖 `langchain_core`**——相关代码在 `langgraph/channels/`、`langgraph/pregel/_algo.py`、`_io.py` 等处，除 `RunnableConfig` 外无外部类型依赖。
2. **依赖集中在 4 个"接缝"**：`RunnableConfig`、`Runnable` 协议、`Graph` 结构类型、callbacks/tracers。**这 4 个接缝全部可以在 opengraph 内用自有类型替代。**
3. **`messages` / `tools` / `language_models` 的引用全部在 `langgraph/prebuilt/` 与 `langgraph/graph/message.py`**——即"预置 agent 装配"与"消息归约器"，这两块**本就不该在 opengraph 内核**（归 openchain）。

#### 3.3.2 「不装 langchain 也能跑图」的路径

**存在，且已被本报告实测验证**：

- Q3 实跑（E3/Q3 E9）：`from langgraph.graph import StateGraph, START, END` + `typing_extensions` 即可跑通完整 quickstart，**全程未 import `langchain`**（只有 `langchain_core` 被间接引入，因为 `langgraph` 依赖它）。
- **理论上更进一步**：若 opengraph 自己实现 `RunnableConfig`/`Runnable`/`Graph` 三个类型，则 `langgraph` 的 `graph`/`pregel`/`channels` 子树可被移植到零 `langchain_core` 依赖的状态——**这正是 opengraph 应当做的事**。

**结论**：**「图层是否真的需要 LangChain」的答案是：不需要 LangChain（`langchain` 包），也不需要 `langchain-core`；只需重写 4 个接缝类型。**

### 3.4 内核最小契约清单（**openchain 的设计输入**）

> 下表是 opengraph 对上（openchain）与对下（用户/脚本）承诺的完整清单。
> 「对下承诺」列中标注 🔴 的项，是 §2.6 验收契约（`harness/demo/target.py`）要求的**必须同名同签名**项。

| # | 契约项 | 最小要求 | LangChain 特有 or 通用 | opengraph 对上承诺 | opengraph 对下承诺 | 证据 |
|---|---|---|---|---|---|---|

## 5. 对 opengraph / openchain 的直接启示（可执行）

1. **把 §3.4 的 C1–C26 清单直接转成 opengraph 的 `Protocol` 定义**（`typing.Protocol` + `runtime_checkable`），放在 `opengraph/protocols.py`。这既是 opengraph 的对外契约，也是 **openchain 的设计输入**（openchain 只依赖这些 Protocol，不依赖 opengraph 的内部实现）。
2. **opengraph 内核的 5 个必须自有类型**：`RunConfig`（替 `RunnableConfig`）、`Node`/`CompiledGraph` 协议（替 `Runnable`）、`Graph`（替 `langchain_core.runnables.graph.Graph`）、`Command`/`Interrupt`（替 `langgraph.types`）、`TraceSink`（替 callbacks）。**这 5 个是"接缝"，其余全部通用。**
3. **C4（稀疏状态）必须写成一条显式的回归测试**：`assert "llm_calls" not in node_input` 且 `node_input.get("llm_calls", 0) == 0`。这是最容易实现错、且会静默破坏 `target.py` 的一条契约。
4. **C8（条件边读 `fresh` 状态）必须同样写成回归测试**：条件边必须能看到本节点刚写的值，否则 `should_continue` 会读到旧的 `messages`，`target.py` 的 tool 循环会失效。
5. **openchain 的适配层职责（由本清单推出）**：① 提供 `openchain.messages` 的消息类型与 `add_messages` 等价归约器；② 提供 `openchain.tools` 的 `@tool`；③ 提供 `openchain.chat_models` 的 provider 抽象与 `init_chat_model` 等价物；④ 把 `AnyMessage` 映射到 opengraph 的鸭子类型契约（C4 的 `tool_calls` 结构）；⑤ 把 `RunnableConfig` 映射到 `RunConfig`（只保留 `thread_id` / `metadata` / `tags`）。
6. **通用协议部分（`tool_calls` 结构、`invoke` 契约、`Annotated` 归约器、`Command`/`interrupt` 语义）openchain 可直接采用，无需适配层**——这是"把 LangChain 与 LangSmith 一起替换掉"在技术上可行的关键证据。
7. **C24（`current_span()`）应作为 opengraph v1 的必需项**（不是 v2）：DeepAgents 的 subagent 机制已经证明"嵌套观测"是硬需求（Q5 §3.2），opengraph 若不提供，未来 openchain 做多 agent 时会被迫引入 `langsmith`。
